# Phase 3 — Dataset Generation

## 1. Objective

The objective of Phase 3 is to build an automated pipeline that collects Industrial IoT telemetry from the simulated factory, processes the MQTT messages, assigns attack labels, stores the resulting records, and exports them as a machine-learning-ready CSV dataset.

---

## 2. Dataset Generation Architecture

The dataset-generation workflow consists of the following components:

- Factory Simulator
- Simulation Runner
- MQTT Broker
- MQTT Collector
- Message Parser
- Dataset Manager
- Labeler
- Dataset Writer
- CSV Exporter
- Attack Runner

The overall flow is:

Factory Simulator  
→ MQTT Broker  
→ MQTT Collector  
→ Message Parser  
→ Labeler  
→ Dataset Writer  
→ CSV Exporter  
→ LightX-IDS Dataset

Attack scenarios are executed alongside the simulator and provide the attack-state information required for labeling.

---

## 3. Automatic Dataset Generation

The main dataset-generation entry point is `generate_dataset.py`.

The workflow performs the following steps:

1. Creates the factory simulator.
2. Creates the dataset preprocessing pipeline.
3. Creates the attack runner.
4. Starts the factory simulator.
5. Allows the simulator time to initialize.
6. Starts the preprocessing pipeline.
7. Executes randomized attack scenarios.
8. Continues until the target dataset size is reached.
9. Exports the collected records to CSV.
10. Stops the preprocessing pipeline.
11. Stops the factory simulator.

---

## 4. Dataset Target

The current dataset-generation configuration specifies:

- Target records: `100,000`
- Output dataset: `dataset/lightx_ids_dataset.csv`

The `AttackRunner` monitors the number of records collected through the `DatasetWriter`.

Dataset generation continues while:

`record_count < TARGET_RECORDS`

The attack runner also checks the record count before starting individual attacks so that generation can stop once the target is reached.

---

## 5. Normal Traffic Generation

Normal traffic is generated by allowing the industrial simulator to operate without an active attack.

The duration of each normal-traffic period is randomized between:

- Minimum: 15 seconds
- Maximum: 40 seconds

This produces varying intervals of legitimate industrial activity instead of a fixed normal-to-attack pattern.

---

## 6. Attack Traffic Generation

Attack traffic is generated using the attack framework developed in Phase 2.

The available attacks are:

- DoS
- Replay
- Injection
- Spoofing

The attack runner randomizes the order of these attack types during each generation cycle.

Each attack receives a randomized duration between:

- Minimum: 5 seconds
- Maximum: 12 seconds

After an attack finishes, a randomized cooldown period is introduced.

---

## 7. Cooldown Period

The cooldown period separates attack scenarios from subsequent traffic.

The current configuration uses:

- Minimum cooldown: 10 seconds
- Maximum cooldown: 25 seconds

The cooldown allows the simulator to return to normal operating conditions before the next attack scenario.

---

## 8. MQTT Traffic Collection

The `MQTTCollector` receives sensor traffic from the MQTT broker.

For every received MQTT message, the collector records:

- Timestamp
- Topic
- Payload
- QoS
- Retain flag

These values are stored in a `RawMQTTMessage` object and forwarded to the dataset manager.

---

## 9. Message Parsing

The `MessageParser` converts raw MQTT messages into structured sensor records.

The parser:

1. Decodes the MQTT payload as JSON.
2. Verifies that the payload is a dictionary.
3. Extracts the sensor information.
4. Converts the sensor value to a floating-point value.
5. Creates a `ParsedSensorRecord`.

The parsed record contains:

- Timestamp
- Topic
- Device ID
- Sensor type
- Sensor value
- Unit
- Status

Invalid JSON, missing values, incompatible data types, and invalid numeric values are rejected from further processing.

---

## 10. Attack-State Processing

The `DatasetManager` monitors the configured attack-state MQTT topic.

When an attack-start event is received, the manager stores:

- `attack_active = True`
- The corresponding `attack_type`

When an attack-stop event is received:

- `attack_active = False`
- `attack_type = None`

This allows the dataset-generation pipeline to associate incoming sensor telemetry with the currently active attack scenario.

Invalid attack-state JSON messages are ignored and reported.

---

## 11. Dataset Labeling

The `Labeler` converts parsed sensor records into final labeled records.

The binary label is determined from the current attack state:

- `0` — Normal
- `1` — Attack

When an attack is active, the corresponding attack type is stored in `attack_type`.

For normal traffic, `attack_type` is `None`.

The labeler also assigns a sequential record number to every generated record.

---

## 12. Final Dataset Schema

The final generated records use the `LabeledRecord` schema.

The fields are:

| Field | Description |
|---|---|
| `timestamp` | Timestamp associated with the sensor record |
| `topic` | MQTT topic from which the message was received |
| `device_id` | Industrial device identifier |
| `sensor_type` | Type of sensor producing the reading |
| `value` | Sensor measurement |
| `unit` | Measurement unit |
| `status` | Sensor/status information |
| `attack_type` | Attack category when an attack is active |
| `label` | Binary normal/attack label |
| `source` | Data source |
| `sequence_number` | Sequential record identifier |

The `source` field is currently set to `simulator`.

---

## 13. Dataset Storage

The `DatasetWriter` temporarily stores labeled records in memory.

Its responsibilities are:

- Add new records
- Return all records
- Clear stored records
- Report the current record count

The writer therefore provides the intermediate storage layer between labeling and CSV export.

---

## 14. CSV Export

The `CSVExporter` converts the collected `LabeledRecord` objects into a CSV file.

The exporter:

1. Checks whether records are available.
2. Opens the configured output file.
3. Creates CSV columns from the labeled-record fields.
4. Writes the header.
5. Writes each labeled record.
6. Reports successful dataset export.

The current automatic-generation output path is:

`dataset/lightx_ids_dataset.csv`

---

## 15. Configuration

Dataset-generation parameters are maintained in `generation_config.py`.

Current configuration:

| Parameter | Value |
|---|---:|
| Target records | 100,000 |
| Minimum normal duration | 15 seconds |
| Maximum normal duration | 40 seconds |
| Minimum attack duration | 5 seconds |
| Maximum attack duration | 12 seconds |
| Minimum cooldown | 10 seconds |
| Maximum cooldown | 25 seconds |

The configured attack weights are:

| Attack | Weight |
|---|---:|
| DoS | 25% |
| Replay | 25% |
| Injection | 25% |
| Spoofing | 25% |

The current `AttackRunner` implementation randomizes attack order using shuffling.

---

## 16. Dataset Generation Sequence

A typical generation cycle follows this pattern:

1. Generate normal industrial traffic.
2. Randomize the available attack order.
3. Execute the first attack.
4. Wait for attack completion.
5. Apply cooldown.
6. Execute the next randomized attack.
7. Apply cooldown.
8. Continue normal traffic.
9. Repeat the cycle until 100,000 records are collected.

This produces a dataset containing both normal and attack-associated sensor telemetry.

---

## 17. Error and Interruption Handling

The automatic dataset generator handles `KeyboardInterrupt`.

If dataset generation is interrupted, the `finally` block still attempts to:

- Export the records collected so far.
- Stop the preprocessing pipeline.
- Stop the factory simulator.

This reduces the possibility of losing already collected records when generation is manually interrupted.

## 21. Phase 3 Outcome

Phase 3 establishes the complete pipeline for generating labeled Industrial IoT traffic from the LightX-IDS simulator.

The resulting dataset contains structured sensor telemetry together with binary attack labels and attack-type information, providing the foundation for dataset engineering, machine-learning training, evaluation, and IDS development in subsequent phases.
